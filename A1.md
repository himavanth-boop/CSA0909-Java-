A1.1 – Represent the Record (2 Marks)
We need to design two file formats: a delimited text file and a binary file using DataOutputStream.
(a) Delimited Text File
Use a comma-separated values (CSV) format.
Field order:

Field	Data type	Example
Pass ID	String	P1001
Register Number	String	192311001
Name	String	Arun Kumar
Route Number	Integer	12
Boarding Stop	String	Central Bus Stop
Validity Date	String	2027-06-30
Amount Paid	Double	4500.00
Example record:
P1001,192311001,Arun Kumar,12,Central Bus Stop,2027-06-30,4500.00
Handling delimiters inside names:
•	If a name contains a comma, enclose the field in double quotes.
•	For example: "Arun, Kumar".
•	If a name contains double quotes, escape them by doubling the quotes.
•	Use a proper CSV parser when reading quoted fields.

(b) Binary File using DataOutputStream
The binary file stores data in a fixed sequence using DataOutputStream.

Field	DataOutputStream method	Storage
Pass ID	writeUTF()	Modified UTF-8
Register Number	writeUTF()	Modified UTF-8
Name	writeUTF()	Modified UTF-8
Route Number	writeInt()	4 bytes
Boarding Stop	writeUTF()	Modified UTF-8
Validity Date	writeUTF()	Modified UTF-8
Amount Paid	writeDouble()	8 bytes

Example Java code:
import java.io.*;

public class BinaryPassWriter {
    public static void main(String[] args) throws IOException {

        DataOutputStream dos = new DataOutputStream(
            new FileOutputStream("passes.dat")
        );

        dos.writeUTF("P1001");
        dos.writeUTF("192311001");
        dos.writeUTF("Arun Kumar");
        dos.writeInt(12);
        dos.writeUTF("Central Bus Stop");
        dos.writeUTF("2027-06-30");
        dos.writeDouble(4500.00);

        dos.close();

        System.out.println("Bus pass saved successfully.");
    }
}
Difference: A text file is human-readable and easy to edit, whereas a binary file is compact and must be read using the same field order and compatible data types.
A1.2 – Design the Operations (3 Marks)
For the text-file design, we use buffered character streams because the records are stored as readable text, and buffering reduces repeated file-access operations.
1. Add a New Pass
Stream classes: FileWriter, BufferedWriter
Pseudocode:
ALGORITHM AddNewPass(pass)

BEGIN
    OPEN the file using FileWriter in append mode
    WRAP FileWriter with BufferedWriter

    CONVERT all pass fields into CSV format

    WRITE the formatted record into the file
    WRITE a new line

    CLOSE BufferedWriter

    DISPLAY "Pass added successfully"
END
Explanation:
•	FileWriter writes character data into the file.
•	BufferedWriter improves writing efficiency.
•	Append mode preserves existing records.
2. Find a Pass by Pass ID
Stream classes: FileReader, BufferedReader
Pseudocode:
ALGORITHM FindPass(passID)

BEGIN
    OPEN the file using FileReader
    WRAP FileReader with BufferedReader

    WHILE a line can be read
        PARSE the CSV record

        IF the record is damaged
            SKIP the record
        ELSE IF record.passID = passID
            DISPLAY the matching pass
            CLOSE BufferedReader
            RETURN
        END IF
    END WHILE

    DISPLAY "Pass not found"

    CLOSE BufferedReader
END
Explanation:
•	FileReader reads character data.
•	BufferedReader reads complete lines efficiently.
•	Each record is checked until the required pass ID is found.

3. List All Passes on a Given Route
Stream classes: FileReader, BufferedReader
Pseudocode:
ALGORITHM ListPassesByRoute(routeNumber)

BEGIN
    OPEN the file using FileReader
    WRAP FileReader with BufferedReader

    found ← FALSE

    WHILE a line can be read
        PARSE the CSV record

        IF the record is damaged
            SKIP the record
        ELSE IF record.routeNumber = routeNumber
            DISPLAY the record
            found ← TRUE
        END IF
    END WHILE

    IF found = FALSE
        DISPLAY "No passes found for this route"
    END IF

    CLOSE BufferedReader
END
Explanation:
•	The program reads every record sequentially.
•	It compares the route number with the requested route.
•	Matching records are displayed.
A1.3 – Design for Damaged Data (2 Marks)
The file system must handle errors without crashing or losing existing records.

Problem	Detection	Handling
Damaged line	Incorrect number of fields or invalid data type	Skip the damaged record and log the line number
Missing file	FileNotFoundException or file existence check	Display an error or create a new file when adding records
Incomplete write	Unexpected end of file or incomplete final record	Preserve a backup, validate records and recover from the last complete record


Incomplete write protection:
•	Write new data into a temporary file.
•	Flush and close the file.
•	Validate the temporary file.
•	Replace the original file only after successful completion.
•	Keep a backup of the original file until replacement succeeds.
This reduces the risk of losing existing records due to power failure.
Alternative Concept – RandomAccessFile with Fixed-Length Records
Instead of a delimited text file, we can use RandomAccessFile with fixed-length records.
Each record occupies the same number of bytes. For example:

Field	Allocated size
Pass ID	10 bytes
Register Number	15 bytes
Name	40 bytes
Route Number	4 bytes
Boarding Stop	30 bytes
Validity Date	10 bytes
Amount Paid	8 bytes
Total	117 bytes

Assumption: String fields are stored in fixed-width encoded byte fields, padded when necessary.
Finding a record using its index:
RandomAccessFile file =
    new RandomAccessFile("passes.dat", "rw");

int recordSize = 117;
int recordIndex = 5;

file.seek((long) recordIndex * recordSize);
The program directly moves to the required record position.
Complexity Analysis

Operation	Text File	RandomAccessFile
Find by ID	O(n)	O(1) seek by known index
Add a record	O(1) append	O(1) append
List by route	O(n)	O(n) scan
Space	Variable	Fixed record size
Important: RandomAccessFile provides O(1) seeking when the record index is already known. Finding a pass by ID still requires O(n) scanning unless an additional index is maintained.

Space Wastage
•	Fixed-length records reserve the maximum allocated space for every field.
•	Short names and boarding stops leave unused padding bytes.
•	Variable-length text files generally use less space for shorter values.
•	Fixed-length records make direct positioning easier but can waste storage.

Conclusion
The delimited text-file approach is suitable for the university's current bus-pass system because it is readable, simple to maintain and supports sequential operations. RandomAccessFile is more suitable when direct record access is important and fixed-length storage is acceptable.
